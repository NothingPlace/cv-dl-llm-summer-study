# 本地模型部署学习笔记（local_deploy_notes.md）

本笔记记录本地大模型部署的核心概念、环境配置、模型选择、量化策略、推理测试与常见问题，适合作为“大模型入门三步”中第三步的实践记录。

---

## 一、为什么需要本地部署

云端 API 调用虽然方便，但存在几个无法回避的问题。第一是**数据隐私**，所有输入输出都要上传到服务商服务器，对于涉及敏感信息的场景不可接受。第二是**网络依赖**，国内访问部分海外 API 需要代理，且存在网络延迟和排队等待。第三是**成本问题**，长期高频调用 API 的费用会持续累积，而本地部署只需一次性硬件投入。第四是**模型自由度**，云端只能用服务商提供的模型版本，本地可以任意切换、微调、定制。

本地部署的核心价值就是：**数据不出本地、无需联网、长期成本低、模型完全可控**。代价是需要一定的硬件投入和环境配置成本。

---

## 二、本地部署与云端 API 的对比

从数据隐私看，本地部署数据完全不出本机，云端 API 则需上传至服务商服务器。从网络依赖看，本地无需联网，云端必须联网。从成本模式看，本地是一次性硬件投入加电费，云端是按 Token 计费。从模型自由度看，本地可任意切换和微调，云端只能用服务商提供的版本。从延迟看，本地无网络往返，云端存在网络延迟和排队。从硬件门槛看，本地需要高性能 GPU 和大显存，云端只需能发 HTTP 请求的设备。从维护负担看，本地需自行管理模型下载、环境配置和版本更新，云端由服务商全权维护。

---

## 三、硬件环境评估

在开始部署前，首先要评估自己的硬件条件。核心指标是**显存大小**，它直接决定了能跑多大的模型。

如果使用 GPU，需要确认显卡型号和显存容量。入门级显卡（如 RTX 3060，12GB 显存）可以运行 7B 模型的 4-bit 量化版本。中端显卡（如 RTX 4070，12-16GB）可以运行 7B 模型的 FP16 版本或 13B 模型的 4-bit 版本。高端显卡（如 RTX 4090，24GB）可以运行 13B 模型的 FP16 版本或 34B 模型的 4-bit 版本。专业级显卡（如 A100，40-80GB）可以运行 70B 模型的 4-bit 版本或 34B 模型的 FP16 版本。

如果没有独立 GPU，也可以使用 CPU 推理，但对内存要求较高。建议至少 32GB 内存，可运行 7B 以下的 GGUF 量化模型。CPU 推理速度较慢，通常在 3-8 Token/秒，适合离线任务或对延迟不敏感的场景。

除了显存和内存，还需要关注磁盘空间。一个 7B 模型的 FP16 权重约 14GB，4-bit 量化后约 3.5GB。如果要保存多个模型，建议预留 100GB 以上磁盘空间。

---

## 四、模型格式选择

本地模型的存储格式主要有几种，各有适用场景。

**Hugging Face 格式（safetensors）** 是官方标准格式，兼容性最好，支持分片存储，适合训练、微调和研究调试。缺点是文件较大，加载较慢。

**GGUF 格式** 是 llama.cpp 系列使用的格式，专为 CPU 和边缘设备优化，支持多种量化级别，加载速度快，内存占用低。适合 CPU 推理、树莓派等低功耗设备。

**GPTQ 格式** 是针对 GPU 的 4-bit 量化格式，由 AutoGPTQ 库支持。适合 GPU 显存受限时的高效推理，速度较快。

**AWQ 格式** 是激活感知权重量化，比 GPTQ 在某些场景下表现更优，也是 GPU 推理的常见选择。

**ONNX 格式** 是跨平台开放标准，支持多种硬件加速，适合跨平台部署和边缘设备。

对于初学者，如果使用 GPU，推荐 GPTQ 或 AWQ 的 4-bit 量化模型；如果使用 CPU，推荐 GGUF 的 Q4_K_M 或 Q5_K_M 量化模型。

---

## 五、量化策略

量化是本地部署中最关键的技术之一。它通过降低模型权重的精度来减少显存占用和模型体积，代价是轻微的性能损失。

从精度等级看，FP32 是全精度，占用 100% 显存，无精度损失，主要用于训练。FP16 或 BF16 是半精度，占用 50% 显存，精度损失极小，是大多数推理场景的首选。INT8 是 8 位量化，占用 25% 显存，精度损失较小，适合显存受限时使用。INT4 是 4 位量化，占用 12.5% 显存，精度损失中等，适合显存极度受限时使用。INT2 或 NF2 是 2 位量化，占用 6.25% 显存，精度损失较大，仅适合极端边缘设备。

以 7B 模型为例，FP32 下约占用 28GB 显存，需要 A100 以上显卡。FP16 下约 14GB，需要 RTX 4090。INT8 下约 7GB，RTX 3060 可运行。INT4 下约 3.5GB，RTX 2060 可运行。INT2 下约 1.75GB，大部分笔记本独显可运行。

需要注意的是，以上仅为模型权重的纯占用估算。实际推理时还需额外预留 20%-40% 显存用于 KV Cache 和中间激活。特别是长上下文场景，KV Cache 的占用会随上下文长度线性增长，可能超过模型权重本身的占用。

量化方法的选择上，如果显存充足（如 A100 80GB），直接用 FP16 或 BF16，质量最优。如果显存中等（如 24GB），用 INT8 或 4-bit GPTQ，平衡质量与占用。如果显存紧张（如 8-12GB），用 4-bit GGUF 或 GPTQ，优先保证能运行。如果使用 CPU 推理，用 GGUF 的 Q4_K_M 或 Q5_K_M，llama.cpp 原生支持。

## 六、推理框架选择

本地推理框架的选择直接影响部署难度和推理性能。

**llama.cpp** 是 C++ 实现，支持 GGUF 格式，CPU 推理性能优秀，适合树莓派等低功耗设备。它的优势是轻量、无依赖、跨平台，缺点是 GPU 支持相对有限。

**Ollama** 是开箱即用的封装工具，内置模型管理，一条命令即可下载和运行模型。适合个人电脑快速体验本地模型，缺点是定制化能力较弱。

**vLLM** 是高吞吐量推理框架，使用 PagedAttention 优化，适合高性能 GPU 推理和生产环境服务。它的优势是速度快、支持连续批处理，缺点是配置较复杂。

**Transformers（Hugging Face）** 是官方 Python 库，功能最全，支持所有格式，适合研究、开发和调试。缺点是推理速度不如专用框架。

**Text Generation WebUI** 是图形化界面，上手简单，适合非技术人员体验本地模型。

对于初学者，推荐从 Ollama 开始，快速体验本地模型。有一定经验后，可以尝试 llama.cpp（CPU）或 vLLM（GPU）做更深入的实验。

## 七、推理速度评估

推理速度的核心指标有几个。**首 Token 延迟（TTFT）** 是从输入到输出第一个 Token 的时间，影响流畅感。**每个 Token 耗时** 是每生成一个 Token 的平均耗时，决定生成速度。**Token 生成率** 是每秒生成的 Token 数量，是最常用的指标。

不同硬件配置下的速度差异很大。旗舰 GPU（H100/A100）跑 7B 模型 FP16，可达 80-120 Token/秒，体验极佳。旗舰消费卡（RTX 4090）跑 7B 模型 FP16，约 50-70 Token/秒，非常流畅。中端消费卡（RTX 4060）跑 7B 模型 INT4，约 30-50 Token/秒，较流畅。入门独显（RTX 3060）跑 7B 模型 INT4，约 15-25 Token/秒，能接受。高端 CPU 跑 7B 模型 GGUF Q4，约 5-10 Token/秒，可读但偏慢。中端 CPU 跑 3B 模型 GGUF Q4，约 3-5 Token/秒，偏慢。低功耗设备（树莓派/手机）跑 1.5B 以下模型，约 1-3 Token/秒，极慢。

影响推理速度的因素中，硬件计算能力影响最大，其次是模型参数量、量化精度、上下文长度、推理框架优化、Batch Size 和解码策略。其中上下文长度的影响容易被忽略——Attention 计算复杂度是 O(N²)，上下文越长，推理越慢。

## 八、CPU 推理与 GPU 推理差异

CPU 和 GPU 推理的本质差异在于计算范式。GPU 有数千个核心，适合大规模并行矩阵运算；CPU 只有少数核心，适合串行逻辑控制和小矩阵运算。这导致 GPU 在深度学习推理上快 5-20 倍。

从显存和内存看，GPU 使用专用显存，带宽极高（如 H100 达 3.35 TB/s）；CPU 使用系统内存，带宽相对低（如 DDR5 约 100 GB/s）。这个带宽差异是 GPU 速度优势的根本原因。

从适用场景看，GPU 适合模型规模大于 7B、需要低延迟响应、高并发、长上下文、多模态处理的场景。CPU 适合没有 GPU、数据隐私要求高、推理延迟不敏感、模型较小（≤3B）、边缘设备部署、成本敏感的大规模部署。

CPU 推理也有优化技术。GGUF 量化是专为 CPU 设计的格式，内存布局优化。OpenVINO 是 Intel 官方推理引擎，利用 AVX-512 和 AMX 指令集。ONNX Runtime 支持 CPU 专用图优化。MKL 和 oneDNN 是 Intel 数学核心库，加速矩阵乘法。编译时启用 AVX2 或 AVX-512 指令集也能提升性能。

## 九、部署实践步骤

本地部署的完整流程可以概括为以下几步。

**第一步：环境准备。** 确认硬件条件（GPU 型号、显存、内存、磁盘），安装必要的软件（Python、CUDA、PyTorch 或 llama.cpp）。如果使用 GPU，确认 CUDA 版本与 PyTorch 兼容。

**第二步：选择模型和格式。** 根据硬件条件选择合适的模型规模（1.5B / 3B / 7B / 13B）和量化格式（FP16 / INT8 / INT4）。从 Hugging Face 或 ModelScope 下载模型权重。

**第三步：选择推理框架。** 根据使用场景选择框架。快速体验用 Ollama，CPU 推理用 llama.cpp，GPU 高性能用 vLLM，研究调试用 Transformers。

**第四步：加载模型并测试。** 加载模型后，先用简单问题测试是否能正常推理。观察首 Token 延迟和生成速度，确认在可接受范围内。

**第五步：性能调优。** 如果速度不够快，尝试降低量化精度、缩短上下文长度、减小 Batch Size、使用更优的推理框架。

**第六步：记录测试结果。** 记录模型名称、量化格式、硬件配置、推理速度、显存占用、输出质量，作为本地部署的测试记录。

## 十、常见问题与排查

**问题一：显存不足（OOM）。** 表现为加载模型时报错或推理中途崩溃。解决方法是降低量化精度（FP16 → INT8 → INT4）、减小 Batch Size、缩短上下文长度、使用 CPU Offloading 将部分层放至内存。

**问题二：推理速度过慢。** 表现为 Token 生成率低于 5 Token/秒。解决方法是使用 GPU 替代 CPU、降低量化精度、使用更优推理框架（如 vLLM）、缩短上下文长度。

**问题三：模型输出质量差。** 表现为回答混乱、重复、答非所问。解决方法是提高量化精度（INT4 → INT8 → FP16）、调整 Temperature 和 Top-p、检查 Prompt 设计是否合理。

**问题四：模型加载失败。** 表现为格式不兼容或文件损坏。解决方法是确认模型格式与推理框架匹配、重新下载模型文件、检查磁盘空间是否充足。

**问题五：CUDA 版本不兼容。** 表现为 PyTorch 无法调用 GPU。解决方法是确认 CUDA 版本与 PyTorch 版本匹配、重新安装对应版本的 PyTorch、检查显卡驱动是否为最新。

**问题六：中文支持差。** 表现为中文回答质量明显低于英文。解决方法是选择中文优化模型（如 Qwen、ChatGLM、DeepSeek）、使用中文 Prompt、必要时微调。

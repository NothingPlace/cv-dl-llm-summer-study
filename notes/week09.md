# 大模型 API 调用核心概念笔记

## 一、API 调用全景总览

调用大模型 API（如 OpenAI、Claude、智谱 GLM、通义千问等）时，最核心的交互要素可以概括为以下八项：

| 概念 | 作用 | 类比 |
| :--- | :--- | :--- |
| **API Key** | 身份认证，证明你有权限调用该服务 | 大门的钥匙 |
| **Base URL** | 服务器地址，告诉请求往哪里发 | 大门的地址 |
| **Model** | 指定用哪个模型来处理请求 | 找哪位专家来处理问题 |
| **Messages** | 传递对话历史，包含用户问题和系统指令 | 与专家的完整对话记录 |
| **Temperature** | 控制回答的随机性和创造性 | 专家的"发散程度" |
| **Max Tokens** | 限制回答的最大长度 | 专家最多能说多少话 |
| **结构化输出** | 强制模型按指定格式（如 JSON）返回 | 要求专家填表格而非自由发言 |
| **Prompt 模板管理** | 将常用提示词模板化、版本化管理 | 预设好的工作流程或问卷模板 |

## 二、API Key（密钥/令牌）

### 2.1 定义与作用

- **API Key** 是一个唯一的加密字符串，用于**身份认证**和**权限控制**。
- 每次调用 API 时，请求头（Header）中必须携带该 Key，服务端验证通过后才会处理请求。
- 同时承担**计费标识**功能——所有消耗的 Token 费用会记录在该 Key 对应的账户下。

### 2.2 使用规范

| 规范 | 说明 |
| :--- | :--- |
| **严禁硬编码** | 不能把 API Key 直接写在代码里（尤其是公开的 GitHub 仓库），否则会被盗刷 |
| **环境变量存储** | 应存放在 `.env` 文件或系统环境变量中，通过 `os.getenv()` 等方式读取 |
| **定期轮换** | 建议定期更换 Key，降低泄露后的风险 |
| **权限最小化** | 不同 Key 分配不同权限（如只读、仅限某个模型），避免一个 Key 拥有全部权限 |
| **用量监控** | 平台通常提供用量仪表盘，需定期检查是否有异常调用 |

### 2.3 常见 API Key 获取方式

- **OpenAI**：platform.openai.com → API Keys → Create new secret key
- **智谱 (GLM)**：open.bigmodel.cn → API Keys
- **通义千问 (Qwen)**：dashscope.aliyun.com → API-KEY 管理
- **DeepSeek**：platform.deepseek.com → API Keys

> ⚠️ **安全红线**：API Key 等同于密码。泄露后他人可用你的额度调用模型，造成经济损失。

## 三、Base URL（基础地址）

### 3.1 定义与作用

- **Base URL** 是 API 服务的基础网络地址，客户端将请求发送到该地址下的特定端点（Endpoint）。
- 不同服务商、不同区域（国内/国外）的 Base URL 各不相同。
- 它决定了你的请求"往哪里发"。

### 3.2 典型 Base URL 示例

| 服务商 | Base URL |
| :--- | :--- |
| OpenAI | `https://api.openai.com/v1` |
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| DeepSeek | `https://api.deepseek.com/v1` |
| 本地部署（Ollama） | `http://localhost:11434/v1` |

### 3.3 为什么需要配置 Base URL

| 场景 | 说明 |
| :--- | :--- |
| **换服务商** | 从 OpenAI 切换到 Azure OpenAI 或国内模型，仅需修改 Base URL 和 API Key，代码逻辑不变 |
| **代理中转** | 国内用户访问 OpenAI 需要代理，Base URL 可配置为代理地址 |
| **本地部署** | 使用私有化部署的模型（如 Ollama、vLLM）时，指向本地或内网地址 |
| **兼容层** | 许多国产模型兼容 OpenAI API 格式，只需更换 Base URL 即可复用现有工具链 |

## 四、Model（模型选择）

### 4.1 定义与作用

- **Model** 参数指定本次请求使用哪个大语言模型。
- 不同模型的**能力、速度、价格、上下文窗口大小**均不同。

### 4.2 主流模型对比

| 模型 | 特点 | 适用场景 |
| :--- | :--- | :--- |
| **GPT-4o** | 多模态（文本+图像），速度快，推理能力强 | 复杂任务、多模态理解 |
| **GPT-4o-mini** | 轻量版，成本低，速度快 | 日常对话、简单任务 |
| **Claude 3.5 Sonnet** | 长上下文（200K），代码能力强 | 代码生成、长文档分析 |
| **DeepSeek-V3** | 高性价比，中文友好 | 中文任务、经济型方案 |
| **智谱 GLM-4** | 国产合规，工具调用能力强 | 国内企业应用 |
| **通义千问 Qwen-Max** | 阿里云生态，中文理解优秀 | 国内业务场景 |

### 4.3 选型原则

```text
简单任务（分类/摘要）→ 轻量模型（mini 版）→ 省成本
复杂任务（推理/创作）→ 旗舰模型（Pro/Max 版）→ 求质量
大批量离线任务 → 平衡成本与速度，批量调用
生产环境 → 稳定版本 + 降级备选模型
```

## 五、Messages（消息体系）

### 5.1 定义与作用

- **Messages** 是 API 请求中最核心的部分，它包含了**完整的对话上下文**。
- 它是一个消息列表，按时间顺序组织，模型基于这些历史消息生成回复。

### 5.2 角色体系

| 角色 | 名称 | 作用 | 谁写的 |
| :--- | :--- | :--- | :--- |
| **system** | 系统指令 | 设定模型的"人设"、行为准则、回复格式约束 | 开发者 |
| **user** | 用户消息 | 用户提出的问题或指令 | 用户 |
| **assistant** | 助手回复 | 模型之前的回复（多轮对话中用于延续上下文） | 模型 |

### 5.3 对话结构示例（文字描述）

**单轮对话结构**：

```text
[
  system: 你是一位专业的 Python 编程助手。
  user: 如何用 Python 读取 CSV 文件？
]
```

**多轮对话结构**：

```text
[
  system: 你是一位友好的客服。
  user: 我的订单什么时候到？          ← 第 1 轮用户提问
  assistant: 您的订单预计明天送达。    ← 第 1 轮助手回答
  user: 能帮我查下具体几点吗？        ← 第 2 轮用户追问
  assistant: 预计下午 3 点左右。      ← 第 2 轮助手回答
  user: 好的，谢谢。                  ← 第 3 轮
]
```

每轮对话中，**所有历史消息都要传入**，模型才能"记住"前文。

### 5.4 核心要点

| 要点 | 说明 |
| :--- | :--- |
| **上下文延续** | 每次请求都必须携带完整的 Messages 历史，API 本身不保存状态 |
| **Token 消耗** | Messages 越长（历史越多），消耗的 Token 越多，费用越高 |
| **上下文窗口限制** | 所有消息的总 Token 数不能超过模型的 Context Window（如 128K） |
| **system 优先级最高** | system 指令通常比 user 指令有更高权重，模型会优先遵循 |

## 六、Temperature（温度参数）

### 6.1 定义与作用

- **Temperature** 控制模型输出概率分布的"尖锐程度"，直接影响回答的**随机性**和**创造性**。
- 取值范围通常为 `0.0 ~ 2.0`（不同平台略有差异）。

### 6.2 不同取值的效果

| 值域 | 效果描述 | 适用场景 |
| :--- | :--- | :--- |
| **0.0 ~ 0.3** | **确定性最强**。模型几乎总是选择概率最高的词，每次输出高度一致。 | 数学题、代码生成、事实问答、格式校验 |
| **0.5 ~ 0.8** | **平衡模式**。在准确性和多样性之间折中。 | 日常对话、一般文案写作、信息提取 |
| **0.9 ~ 1.5** | **高创造性**。输出更丰富多样，但可能出现"跑题"或逻辑瑕疵。 | 诗歌创作、头脑风暴、广告语生成 |
| **> 1.5** | **极度随机**。可能产生无意义输出，谨慎使用。 | 实验性探索、艺术生成 |

### 6.3 与其他参数的关系

| 参数 | 配合建议 |
| :--- | :--- |
| **Top-p（核采样）** | 通常只调 Temperature 或只调 Top-p，两者不宜同时极端调整。推荐：固定 Top-p=0.9，调节 Temperature |
| **Frequency Penalty** | 高 Temperature 时可配合 Frequency Penalty 降低重复词概率 |
| **Max Tokens** | 与 Temperature 无关，独立控制输出长度 |

### 6.4 直观理解

- **Temperature = 0**：模型永远选择"最稳妥"的下一个词 → 答案确定、可复现
- **Temperature = 1**：模型按原始概率分布采样 → 自然、适度多样
- **Temperature = 2**：模型倾向于选择概率较低（更罕见）的词 → 天马行空、冒险

## 七、Max Tokens（最大输出长度）

### 7.1 定义与作用

- **Max Tokens** 限制模型生成回复的**最大 Token 数量**（不是字数）。
- 当生成达到该上限时，输出会被强制截断。

### 7.2 设置策略

| 策略 | 说明 |
| :--- | :--- |
| **按需设置** | 简单问答设 500，长文生成设 2000-4000，具体取决于任务需求 |
| **预留上下文空间** | Max Tokens + Messages Tokens ≤ Context Window（需预留 buffer） |
| **成本控制** | 输出 Token 数直接决定费用，不宜设置过大的无用上限 |
| **分块生成** | 超长输出（如翻译整本书）应分段调用，而非单次设置极大值 |

### 7.3 注意事项

- **截断风险**：Max Tokens 设置过小时，答案可能在半句处被切断，影响完整性。
- **与 Token 计费的关系**：输出 Token 数按实际生成量计费，而非 Max Tokens 设定值（OpenAI 按实际消耗计费，设定值仅是"上限"）。
- **不同模型差异**：不同模型的默认 Max Tokens 不同，需查官方文档确认。

## 八、结构化输出（Structured Output）

### 8.1 定义与作用

- **结构化输出** 是指强制模型以**预定格式**（通常是 JSON）返回结果，而非自由文本。
- 目的是让输出**可解析、可编程、可自动化处理**。

### 8.2 常见实现方式

| 方式 | 说明 | 可靠性 |
| :--- | :--- | :--- |
| **Prompt 约束** | 在 system 或 user 消息中明确要求"请以 JSON 格式输出" | ⭐⭐ 依赖模型自觉，不稳定 |
| **约束解码** | 用特定库（如 `instructor`、`Outlines`）在解码层强制约束输出格式 | ⭐⭐⭐⭐ 较可靠 |
| **JSON Mode** | 部分模型提供专门的 JSON 模式开关（如 OpenAI 的 `response_format`） | ⭐⭐⭐⭐ 官方支持 |
| **Function Calling** | 通过定义函数 Schema，强制模型按 Schema 返回参数 | ⭐⭐⭐⭐⭐ 最稳定，生产级推荐 |

### 8.3 设计原则

| 原则 | 说明 |
| :--- | :--- |
| **Schema 先行** | 先定义好输出的 JSON 结构（字段名、类型、是否必填） |
| **给示例** | 在 Prompt 中提供 1-2 个正确的 JSON 输出示例（Few-shot） |
| **字段语义清晰** | 字段名用英文下划线命名（如 `user_name`），避免中文键名导致解析问题 |
| **处理异常** | 代码层需对解析失败（如非 JSON 响应）做容错处理 |
| **嵌套控制** | 避免过深的嵌套结构（3 层以上），增加模型输出难度 |

### 8.4 应用场景

| 场景 | 结构化输出示例 |
| :--- | :--- |
| **信息抽取** | `{"姓名": "张三", "公司": "阿里", "职位": "工程师"}` |
| **情感分析** | `{"情感极性": "正面", "置信度": 0.92, "关键词": ["画面", "剧情"]}` |
| **分类标注** | `{"类别": "科技新闻", "子类别": "消费电子", "实体": ["苹果", "iPhone"]}` |
| **实体关系抽取** | `{"头实体": "马斯克", "关系": "创始人", "尾实体": "特斯拉"}` |
| **代码生成** | `{"language": "python", "code": "def foo(): pass", "explanation": "..."}` |

## 九、Prompt 模板管理

### 9.1 定义与作用

- **Prompt 模板** 是将常用的提示词固化为**可复用的结构化文本**，其中包含**固定内容**和**可替换变量**。
- **模板管理** 是对这些模板进行**版本控制、分类存储、效果追踪**的系统化流程。

### 9.2 模板的基本结构

| 组成部分 | 说明 | 示例 |
| :--- | :--- | :--- |
| **固定指令** | 不变的任务描述和约束 | "你是一位专业翻译" |
| **变量占位符** | 动态填充的部分 | `{{source_text}}`、`{{target_language}}` |
| **输出格式约束** | 规定返回格式 | "请返回 JSON 格式" |
| **Few-shot 示例** | 可选，用于提升准确率 | 2-3 个完整示例 |

### 9.3 模板管理最佳实践

| 实践 | 说明 |
| :--- | :--- |
| **分类存储** | 按任务类型分目录存放（如 `translation/`、`summary/`、`extraction/`） |
| **版本控制** | 用 Git 管理模板文件，记录每次修改的原因和效果变化 |
| **变量命名规范** | 使用 `{{double_braces}}` 占位符，与代码变量名称对应清晰 |
| **A/B 测试** | 对同一任务准备多个版本模板，对比输出质量和 Token 消耗 |
| **模板复用** | 建立公共模块（如 "通用系统人设"），在多个模板中复用 |
| **效果追踪** | 记录每个模板在不同模型版本上的表现，便于回滚和优化 |

### 9.4 常见模板类型

| 模板类型 | 适用场景 | 变量示例 |
| :--- | :--- | :--- |
| **翻译模板** | 多语言互译 | `{{source_text}}`, `{{source_lang}}`, `{{target_lang}}` |
| **摘要模板** | 长文档浓缩 | `{{document}}`, `{{max_length}}`, `{{focus}}` |
| **分类模板** | 文本打标 | `{{text}}`, `{{candidate_labels}}` |
| **信息抽取模板** | NER、关系抽取 | `{{text}}`, `{{schema}}` |
| **代码生成模板** | 根据需求生成代码 | `{{requirement}}`, `{{language}}`, `{{framework}}` |
| **角色扮演模板** | 固定人设对话 | `{{character_name}}`, `{{character_description}}` |

### 9.5 模板管理工具

| 方案 | 适用场景 | 特点 |
| :--- | :--- | :--- |
| **纯文本 + Git** | 小规模项目 | 轻量，无学习成本 |
| **LangChain PromptTemplate** | 开发阶段 | 与代码紧密集成，支持 Few-shot 自动组装 |
| **Pinecone / 向量数据库** | 大规模模板库 | 支持语义检索，根据输入自动匹配最合适的模板 |
| **Prompt 管理平台** | 团队协作 | 如 PromptLayer、HumanLoop，支持在线编辑和效果追踪 |

## 十、综合调用流程（概念梳理）

一个完整的 API 请求处理流程如下：

```text
步骤 1：配置环境
├── 从环境变量读取 API Key
├── 根据服务商配置 Base URL
└── 确认网络连通性（代理/VPN 状态）

步骤 2：选择模型
├── 根据任务复杂度选择合适模型
└── 确认该模型是否支持所需功能（如 JSON Mode）

步骤 3：构建 Messages
├── 从模板库加载 system 指令
├── 填充变量生成 user 消息
└── 如需多轮对话，拼接历史 assistant 消息

步骤 4：设置生成参数
├── 根据任务类型设定 Temperature
├── 根据回复长度需求设定 Max Tokens
└── 如需结构化输出，配置 JSON Mode 或 Function Calling

步骤 5：发送请求
├── 将上述内容封装为 API 请求体
├── 发送至 Base URL 对应的端点
└── 等待模型响应

步骤 6：处理响应
├── 提取 assistant 回复内容
├── 若为 JSON 格式，进行解析
└── 异常处理（超时、限流、格式错误等）
```

## 十一、常见参数组合建议

| 任务类型 | Model 建议 | Temperature | Max Tokens | 结构化输出 |
| :--- | :--- | :--- | :--- | :--- |
| **事实问答** | 旗舰模型 | 0.0 ~ 0.2 | 500 | 可选 |
| **代码生成** | 代码优化模型 | 0.0 ~ 0.3 | 2000 | 需要 |
| **创意写作** | 旗舰模型 | 0.8 ~ 1.2 | 3000+ | 不需要 |
| **信息抽取** | 轻量/旗舰均可 | 0.0 ~ 0.1 | 500 | **必须** |
| **摘要总结** | 长上下文模型 | 0.3 ~ 0.5 | 根据文档长度 | 可选 |
| **分类打标** | 轻量模型 | 0.0 | 200 | **必须** |
| **翻译** | 多语言优化模型 | 0.1 ~ 0.3 | 根据原文长度 | 不需要 |

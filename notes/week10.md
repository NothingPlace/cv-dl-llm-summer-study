# 本地模型部署与推理核心概念笔记

## 一、本地模型部署全景总览

与调用云端 API 不同，本地部署大模型意味着将模型文件下载到自己的机器上，在本地环境中加载并运行推理。这涉及一系列硬件、软件和优化技术的考量。

| 概念 | 作用 | 类比 |
| :--- | :--- | :--- |
| **本地模型** | 将模型权重文件下载到本地磁盘并加载运行 | 买书放家里随时翻阅，而非每次去图书馆借 |
| **量化** | 压缩模型权重精度（如 FP32 → INT8），减小体积和显存占用 | 将高清照片压缩为缩略图，牺牲一点细节换空间 |
| **显存占用** | 模型运行时所消耗的 GPU 显存大小 | 工作台面积——放不下就干不了活 |
| **推理速度** | 模型生成每个 Token 所需的时间 | 翻书的速度，快则流畅，慢则卡顿 |
| **CPU/GPU 推理差异** | 不同硬件运行模型的效率与可行性对比 | 专业画师用数位板 vs 用鼠标画画 |

## 二、本地模型（Local Model）

### 2.1 定义与作用

- **本地模型** 是指将大语言模型的权重文件下载到用户自己的计算机、服务器或边缘设备上，完全在本地环境中加载、运行和推理。
- 与云端 API 调用相反，本地推理**不依赖互联网连接**，且**数据无需上传到第三方服务器**。

### 2.2 本地模型 vs 云端 API

| 维度 | 本地模型 | 云端 API |
| :--- | :--- | :--- |
| **数据隐私** | ⭐⭐⭐⭐⭐ 数据不出本地，完全可控 | ⭐⭐ 数据需上传至服务商服务器 |
| **网络依赖** | 无需联网 | 必须联网（国内访问 OpenAI 还需代理） |
| **成本模式** | 一次性硬件投入 + 电费 | 按 Token 计费，长期调用成本高 |
| **模型自由** | 可任意切换、微调、定制模型 | 仅能使用服务商提供的模型版本 |
| **延迟** | 本地计算，无网络往返 | 存在网络延迟 + 排队延迟 |
| **硬件门槛** | 需要高性能 GPU 和大显存 | 只需能发 HTTP 请求的设备 |
| **维护负担** | 需自行管理模型下载、环境配置、版本更新 | 服务商全权维护 |
| **并发能力** | 受限于单机硬件资源 | 弹性扩展，可支持高并发 |

### 2.3 常见本地模型格式

| 格式 | 说明 | 适用场景 |
| :--- | :--- | :--- |
| **Hugging Face 格式（safetensors）** | 官方标准格式，兼容性好，支持分片存储 | 训练、微调、研究调试 |
| **GGUF（GPT-Generated Unified Format）** | llama.cpp 系列使用，专为 CPU 和边缘设备优化 | 本地 CPU 推理、移动端部署 |
| **GPTQ** | 针对 GPU 的 4-bit 量化格式，由 AutoGPTQ 库支持 | GPU 显存受限时的高效推理 |
| **AWQ** | 激活感知权重量化，比 GPTQ 在某些场景更优 | GPU 推理，追求极致显存节省 |
| **ONNX** | 跨平台开放标准，支持多种硬件加速 | 跨平台部署、边缘设备 |

### 2.4 主流本地推理框架

| 框架 | 特点 | 适用场景 |
| :--- | :--- | :--- |
| **llama.cpp** | C++ 实现，支持 GGUF，CPU 推理性能优秀 | CPU 推理、树莓派等低功耗设备 |
| **Ollama** | 开箱即用的封装工具，内置模型管理 | 个人电脑快速体验本地模型 |
| **vLLM** | 高吞吐量，PagedAttention 优化 | 高性能 GPU 推理、生产环境服务 |
| **Transformers（Hugging Face）** | 官方 Python 库，功能最全，支持所有格式 | 研究、开发、调试 |
| **llama-factory** | 集训练、微调、推理于一体的全能工具 | 国产模型微调与部署 |
| **Text Generation WebUI** | 图形化界面，上手简单 | 非技术人员体验本地模型 |

## 三、量化（Quantization）

### 3.1 定义与作用

- **量化** 是一种模型压缩技术，将模型权重的**精度降低**（如从 32 位浮点数降到 8 位整数），从而**大幅减少模型体积和显存占用**。
- 代价是**轻微的性能损失**（精度下降通常控制在 1%-3% 以内）。

### 3.2 量化精度等级对比

| 精度格式 | 位数 | 显存占用比例 | 精度损失 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **FP32（全精度）** | 32 位 | 100%（基准） | 无 | 训练、科学研究 |
| **FP16 / BF16** | 16 位 | 50% | 极微 | 大多数推理场景 |
| **INT8（8 位量化）** | 8 位 | 25% | 较小 | 显存受限时的推理 |
| **INT4（4 位量化）** | 4 位 | 12.5% | 中等 | 显存极度受限时 |
| **INT2 / NF2（2 位）** | 2 位 | 6.25% | 较大 | 极端边缘设备、实验性 |

### 3.3 不同精度下 7B 模型的显存占用估算

> 参考基准：7B 参数模型在 FP32 下约占用 28 GB 显存

| 精度 | 计算公式 | 显存占用 | 是否可消费级 GPU 运行 |
| :--- | :--- | :--- | :--- |
| FP32 | 7B × 4 字节 | ~28 GB | ❌ 需 A100（40GB）以上 |
| FP16 / BF16 | 7B × 2 字节 | ~14 GB | ⚠️ 需 RTX 4090（24GB） |
| INT8 | 7B × 1 字节 | ~7 GB | ✅ RTX 3060（12GB）可运行 |
| INT4（GPTQ/AWQ） | 7B × 0.5 字节 | ~3.5 GB | ✅ RTX 2060（6GB）可运行 |
| INT2 / NF2 | 7B × 0.25 字节 | ~1.75 GB | ✅ 大部分笔记本独显可运行 |

> 📌 以上为**模型权重**的纯占用估算，实际推理时还需额外预留 **20%-40% 显存**用于 KV Cache 和中间激活。

### 3.4 量化方法的实际效果（定性对比）

| 量化方法 | 精度保持 | 推理速度 | 显存节省 | 实现复杂度 |
| :--- | :--- | :--- | :--- | :--- |
| **FP16（不量化）** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐⭐（最简单） |
| **GPTQ（4-bit）** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| **AWQ（4-bit）** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| **GGUF（Q4_K_M）** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐（llama.cpp 友好） |
| **INT8（静态量化）** | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐（需校准数据集） |

### 3.5 量化选择的决策逻辑

```text
显存充足（如 A100 80GB）→ 直接用 FP16/BF16 → 质量最优
显存中等（如 24GB）→ INT8 或 4-bit GPTQ → 平衡质量与占用
显存紧张（如 8-12GB）→ 4-bit GGUF/GPTQ → 优先保证运行
CPU 推理 → GGUF（Q4_K_M / Q5_K_M）→ llama.cpp 原生支持
```

## 四、显存占用（VRAM Usage）

### 4.1 显存占用的构成

加载一个模型进行推理时，显存占用由以下三部分构成：

```text
总显存占用 = 模型权重 + KV Cache + 中间激活（推理时）+ 框架开销
```

| 组成部分 | 说明 | 影响因素 |
| :--- | :--- | :--- |
| **模型权重** | 所有参数矩阵的存储 | 参数量 × 精度位数 |
| **KV Cache** | 缓存已生成 Token 的 Key 和 Value 向量 | 上下文长度 × 注意力头数 × 层数 |
| **中间激活** | 前向传播过程中产生的临时张量 | Batch Size × 序列长度 |
| **框架开销** | PyTorch/TensorFlow 等框架的固定占用 | 框架版本、CUDA 版本 |

### 4.2 不同规模模型在各精度下的显存占用参考表

| 模型规模 | FP32 | FP16/BF16 | INT8 | INT4（4-bit） | 建议硬件 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1.5B**（小模型） | ~6 GB | ~3 GB | ~1.5 GB | ~0.8 GB | 多数笔记本独显 |
| **3B**（Phi-3 级别） | ~12 GB | ~6 GB | ~3 GB | ~1.5 GB | RTX 3060（12GB） |
| **7B**（LlaMA 3, Qwen-7B） | ~28 GB | ~14 GB | ~7 GB | ~3.5 GB | RTX 4090（24GB） |
| **13B**（LlaMA 2-13B） | ~52 GB | ~26 GB | ~13 GB | ~6.5 GB | A100（40GB）或双卡 4090 |
| **34B**（Yi-34B） | ~136 GB | ~68 GB | ~34 GB | ~17 GB | 多卡 A100 / H100 |
| **70B**（LlaMA 3-70B） | ~280 GB | ~140 GB | ~70 GB | ~35 GB | 8×A100（80GB） |
| **405B**（最新巨型模型） | ~1.6 TB | ~810 GB | ~405 GB | ~200 GB | 超大规模集群 |

### 4.3 KV Cache 的影响

KV Cache 是推理过程中随上下文长度**线性增长**的显存消耗项。公式概念：

```text
KV Cache 大小 ∝ Batch Size × 上下文长度 × 层数 × 注意力头维度 × 精度
```

**定性示例**（7B 模型，FP16）：

- 上下文 2K：KV Cache ≈ 0.5 GB
- 上下文 8K：KV Cache ≈ 2 GB
- 上下文 32K：KV Cache ≈ 8 GB
- 上下文 128K：KV Cache ≈ 32 GB

> ⚠️ 长上下文场景下，**KV Cache 可能超过模型权重本身的占用**。这就是为什么很多模型"跑得动但一处理长文本就 OOM（显存溢出）"的原因。

### 4.4 显存优化技巧

| 技巧 | 说明 | 效果 |
| :--- | :--- | :--- |
| **量化（最有效）** | 将权重从 FP16 降到 INT4 | 显存占用降低 75% |
| **减少 Batch Size** | 批量推理时降低批次大小 | 线性降低激活显存 |
| **缩短上下文** | 控制输入长度，限制 Max Tokens | 降低 KV Cache 占用 |
| **Flash Attention** | 使用 Flash Attention 优化注意力机制 | 降低 50%-80% 中间激活显存 |
| **PagedAttention（vLLM）** | 将 KV Cache 分页管理，按需分配 | 显著降低碎片化和总占用 |
| **Offloading 到 CPU** | 将部分权重或 KV Cache 放至内存 | 牺牲速度换显存空间 |

## 五、推理速度（Inference Speed）

### 5.1 核心指标

| 指标 | 单位 | 定义 | 重要性 |
| :--- | :--- | :--- | :--- |
| **首 Token 延迟（TTFT）** | 毫秒/秒 | 从输入到输出第一个 Token 的时间 | 影响"流畅感" |
| **每个 Token 耗时（Time per Token）** | 毫秒/Token | 每生成一个 Token 的平均耗时 | 决定生成速度 |
| **生成吞吐量（Throughput）** | Token/秒 | 每秒生成的 Token 数量 | 决定批量处理效率 |
| **Token 生成率（Tokens/s）** | Token/秒 | 最常用指标，越高越快 | 用户体验核心 |

### 5.2 不同场景下的速度参考（定性）

| 硬件配置 | 模型规模 | 精度 | 推理速度（Tokens/s） | 用户体验 |
| :--- | :--- | :--- | :--- | :--- |
| **旗舰 GPU（H100/A100）** | 7B | FP16 | 80-120 Tokens/s | 飞一般的感觉 |
| **旗舰消费卡（RTX 4090）** | 7B | FP16 | 50-70 Tokens/s | 非常流畅 |
| **中端消费卡（RTX 4060）** | 7B | INT4 | 30-50 Tokens/s | 较流畅，可接受 |
| **入门独显（RTX 3060）** | 7B | INT4 | 15-25 Tokens/s | 能接受，轻微等待 |
| **高端 CPU（如 i9 / 128GB 内存）** | 7B | GGUF Q4 | 5-10 Tokens/s | 可读，但偏慢 |
| **中端 CPU（i5 / 32GB 内存）** | 3B | GGUF Q4 | 3-5 Tokens/s | 偏慢，需耐心 |
| **低功耗设备（树莓派 / 手机）** | 1.5B 以下 | INT2/NF2 | 1-3 Tokens/s | 极慢，实验性 |

> 📌 以上为"文本生成"场景下的**生成阶段**速度。**首 Token 延迟**在本地 GPU 上通常为 50-500ms，在 CPU 上可能达到 1-5 秒。

### 5.3 影响推理速度的因素

| 因素 | 影响程度 | 说明 |
| :--- | :--- | :--- |
| **硬件计算能力** | ⭐⭐⭐⭐⭐ | GPU 的 CUDA 核心数、Tensor Core 版本、显存带宽 |
| **模型参数量** | ⭐⭐⭐⭐⭐ | 参数量越大，计算量越大 |
| **量化精度** | ⭐⭐⭐⭐ | INT4 比 FP16 快 2-3 倍（计算更快，数据更小） |
| **上下文长度** | ⭐⭐⭐ | 上下文越长，Attention 计算越慢（O(N²) 复杂度） |
| **推理框架优化** | ⭐⭐⭐ | vLLM 比 Transformers 快 3-5 倍 |
| **Batch Size** | ⭐⭐ | 批量越大，单 Token 平均耗时越短（但总显存消耗增大） |
| **解码策略** | ⭐⭐ | 贪婪解码最快，Beam Search（集束搜索）慢 2-5 倍 |

### 5.4 速度优化技巧

| 优化方法 | 原理 | 速度提升 |
| :--- | :--- | :--- |
| **使用 vLLM** | PagedAttention + 连续批处理 | 2-5 倍于原生 HF |
| **使用 INT4/INT8 量化** | 减少数据量和计算量 | 2-3 倍于 FP16 |
| **Flash Attention 2** | 利用显存层次结构优化 Attention | 1.5-2 倍 |
| **使用 TensorRT-LLM** | NVIDIA 专用推理优化引擎 | 3-5 倍于原生 |
| **减小 Batch Size** | 减少计算负载 | 提升单请求速度 |
| **限制上下文长度** | 缩短 Attention 计算范围 | 显著提升长文本速度 |
| **使用 Speculative Decoding** | 用小模型"猜"大模型加速生成 | 1.5-2 倍 |

## 六、CPU 推理 vs GPU 推理差异

### 6.1 核心差异对比

| 维度 | GPU 推理 | CPU 推理 |
| :--- | :--- | :--- |
| **计算范式** | 大规模并行（数千个核心同时计算矩阵乘法） | 串行或轻度并行（少数核心） |
| **算力密度** | 极高（适合大矩阵运算） | 较低（适合逻辑控制和小矩阵） |
| **显存 vs 内存** | 专用显存（VRAM），带宽极高（如 H100 3.35 TB/s） | 系统内存（DDR），带宽相对低（如 DDR5 ~100 GB/s） |
| **速度差异** | ⭐⭐⭐⭐⭐ 快 5-20 倍（视模型大小） | ⭐⭐ 慢，但可用 GGUF 等格式优化 |
| **硬件门槛** | 需独立 GPU（费用高，功耗大） | 服务器已有 CPU，零额外成本 |
| **功耗** | 高（旗舰卡 300-450W） | 相对低 |
| **可扩展性** | 支持多卡并行（分布式推理） | 可多 CPU 并行但效率远不如 GPU |
| **适用模型规模** | 1B ~ 400B（显存够即可） | 建议 7B 以下，更大需要量化 |
| **软件生态** | CUDA / ROCm 生态成熟 | OpenVINO / llama.cpp / ONNX Runtime |

### 6.2 什么时候选 CPU 推理？

| 场景 | 理由 |
| :--- | :--- |
| **没有 GPU 或 GPU 显存不足** | 服务器本身有 CPU 和内存，无额外硬件成本 |
| **数据隐私/合规要求** | 无法上传到云端，但也不想买显卡 |
| **推理延迟不敏感** | 离线任务、定时批处理 |
| **模型较小（≤ 3B）** | 小模型在 CPU 上也能跑出可接受速度（5-8 Tokens/s） |
| **边缘设备部署** | 树莓派、手机、工业嵌入式设备，无 GPU 可用 |
| **成本敏感的大规模部署** | CPU 服务器比 GPU 服务器便宜得多 |

### 6.3 什么时候必须选 GPU 推理？

| 场景 | 理由 |
| :--- | :--- |
| **模型规模 > 7B** | CPU 推理极慢（< 2 Tokens/s），用户体验无法接受 |
| **需要低延迟响应** | 实时对话、交互式应用，首 Token 延迟需 < 1 秒 |
| **高并发场景** | GPU 可通过批处理（Batching）提升吞吐量 |
| **需要处理长上下文（> 8K）** | Attention 计算量指数级增长，CPU 无法承受 |
| **需要多模态处理** | 图像编码器通常依赖 CUDA 加速 |

### 6.4 CPU 推理优化技术

| 技术 | 说明 | 适用框架 |
| :--- | :--- | :--- |
| **GGUF 量化** | 专为 CPU 设计的量化格式，内存布局优化 | llama.cpp |
| **OpenVINO** | Intel 官方推理引擎，利用 AVX-512 和 AMX 指令集 | OpenVINO |
| **ONNX Runtime** | 跨平台推理，支持 CPU 专用图优化 | ONNX Runtime |
| **MKL / oneDNN** | Intel 数学核心库，加速矩阵乘法 | PyTorch + MKL |
| **AVX2 / AVX-512 指令集** | 利用 CPU 的 SIMD（单指令多数据）指令加速 | 编译时启用 |
| **内存带宽优化** | 使用 NUMA（非统一内存访问架构）绑定，减少跨 socket 访问 | 系统级优化 |

### 6.5 混合推理策略

在实际生产场景中，可以采用混合方案：

```text
策略 1：GPU 主力 + CPU 备选
├── 默认走 GPU（高吞吐、低延迟）
└── GPU 显存不足或故障时降级到 CPU

策略 2：GPU 编码 + CPU 生成
├── 输入编码（Prompt 处理）用 GPU
└── 自回归生成阶段切换到 CPU（适合显存极小场景）

策略 3：多级缓存
├── 热门请求 → GPU 实时生成
└── 冷门请求 → CPU 生成（牺牲速度换 GPU 资源）
```

## 八、常见问题 Q&A（定性解答）

| 问题 | 解答 |
| :--- | :--- |
| **4-bit 量化会损失很多质量吗？** | 对大多数对话任务，4-bit 量化后的质量损失在 1%-3% 以内，绝大多数用户感受不到明显差异。代码生成和数学推理可能稍明显。 |
| **CPU 推理 7B 模型要多久？** | 约 2-5 Token/秒（取决于 CPU 型号和量化级别），阅读速度约 3-5 Token/秒，基本"可读但需耐心"。 |
| **显存和内存可以混用吗？** | 可以开启 GPU Offloading，将部分模型层放至内存，用 CPU 计算。代价是速度会明显下降（内存带宽远低于显存）。 |
| **Mac 能本地跑大模型吗？** | 可以。M1/M2/M3 芯片的"统一内存"可作为显存使用，配合 llama.cpp 的 Metal 加速，性能好于同级别 CPU，接近入门独显。 |
| **多卡推理怎么实现？** | 大模型自动支持模型并行（如 Accelerate、vLLM 的多 GPU 推理）。需注意 NVLink 带宽和卡间通信效率。 |
| **本地模型怎么做流式输出？** | 主流的推理框架（Transformers、vLLM、llama.cpp）均支持 Streaming，逐 Token 返回，无需等全部生成完。 |
| **量化后的模型还能微调吗？** | 可以，但需使用 QLoRA 等技术。直接在量化模型上做全量微调效果较差，通常先微调全精度模型再量化。 |
